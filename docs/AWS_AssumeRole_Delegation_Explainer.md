# AWS 역할 위임(AssumeRole) 인증 — 발표용 개념 설명

> 대상: 발표·데모에서 "왜 바꿨고, 어떻게 동작하는가"를 설명할 때 쓰는 문서.
> 구현 설계·일정은 `docs/IAM_Delegation_and_Team_Budget_Design_2026-09-15.md` 참고.
> 범위 결정(2026-09-15): **AWS만 전환**한다. Azure·GCP는 코드를 건드리지 않는다(§6).

## 1. 무엇이 문제였나

기존 방식은 사용자가 자기 AWS **Access Key ID + Secret Access Key**를 우리 화면에 붙여넣고,
우리가 그걸 DB에 저장한 뒤 필요할 때마다 꺼내 쓰는 구조였다.

우리는 이 값을 **AES-256-GCM으로 암호화해서** 저장하고 있었다(`app/security/credential_crypto.py`).
그래서 "평문 저장"은 아니었다. 그럼에도 문제가 남는 이유는:

| 암호화가 막아주는 것 | 암호화가 못 막는 것 |
|---|---|
| DB 파일·백업만 통째로 유출됐을 때 | **서버가 침해당했을 때** — 서버는 복호화 키를 갖고 있어야 동작하므로, 서버를 잡은 공격자는 전 사용자의 키를 평문으로 얻는다 |
| | **만료가 없다** — 사용자가 직접 폐기하기 전까지 그 키는 영원히 유효하다 |
| | **권한 범위가 키에 종속된다** — 사용자가 관리자 권한 키를 붙여넣으면 우리는 관리자 권한을 통째로 들고 있게 된다 |

정리하면: **"남의 집 열쇠를 복사해서 금고에 보관"하는 구조**였고, 금고가 아무리 튼튼해도
열쇠가 거기 있다는 사실 자체가 위험이었다.

## 2. 무엇으로 바꿨나 — 신뢰의 방향을 뒤집는다

바뀐 방식에서 사용자는 **우리에게 비밀을 주지 않는다.** 대신 자기 AWS 계정 안에
"이 서비스가 들어와도 된다"는 **역할(Role)** 을 만들어 두고, 우리는 그 역할을 필요할 때마다
**1시간짜리로 빌려서** 쓴다.

```
[ 기존 ]
  사용자 ──(영구 열쇠 사본)──▶ 우리 DB ──▶ AWS
          비밀을 넘긴다              계속 보관

[ 변경 후 ]
  사용자 ── 자기 계정에 역할을 만들고 "이 서비스를 신뢰한다"고 선언
                                    ▲
  우리 ───(우리 신원으로 매번 요청)──┘ ──▶ 1시간짜리 임시 자격 ──▶ AWS
          비밀을 받지 않는다              쓰고 나면 사라짐
```

우리가 DB에 저장하는 값은 두 개뿐이고, **둘 다 비밀이 아니다**:

- `role_arn` — 빌릴 역할의 주소 (예: `arn:aws:iam::123456789012:role/MultiCloudOpsAccess`)
- `external_id` — 사용자와 우리만 공유하는 확인용 값

이 두 값이 통째로 유출돼도 **공격자는 아무것도 할 수 없다.** 역할을 빌리려면 "우리 서비스의
AWS 신원"으로 요청해야 하는데, 그건 유출된 값 안에 없기 때문이다.

## 3. 알아야 할 IAM 개념 4가지

### ① IAM 사용자 vs IAM 역할

| | IAM 사용자(User) | IAM 역할(Role) |
|---|---|---|
| 소유자 | 특정 사람/시스템에 고정 | **없다.** 조건을 만족하는 누구나 빌려 쓴다 |
| 자격증명 | Access Key (만료 없음) | 빌릴 때마다 발급되는 **임시 자격** (기본 1시간) |
| 비유 | 내 이름이 박힌 사원증 | 공용 출입 배지 — 자격을 증명하면 빌려주고, 시간이 지나면 회수 |

역할 위임의 핵심은 **"만료되지 않는 것"에서 "만료되는 것"으로 옮기는 것**이다.

### ② 역할에 붙는 정책은 두 종류다 (여기가 제일 헷갈리는 지점)

```
IAM 역할 ─┬─ 신뢰 정책 (Trust Policy)   : "누가 이 역할을 빌릴 수 있나"
          └─ 권한 정책 (Permission Policy): "이 역할로 무엇을 할 수 있나"
```

- **신뢰 정책**은 역할에만 있는 개념이다. 여기에 우리 서비스의 AWS 계정 ID가 들어간다.
  → 이게 바로 **"사용자가 우리를 신뢰한다"고 선언하는 자리**다.
- **권한 정책**은 EC2를 만들 수 있는지, S3를 지울 수 있는지를 정한다. 사용자가 여기서 범위를
  좁히면 우리는 그 이상 아무것도 못 한다. → **권한의 상한선을 우리가 아니라 사용자가 쥔다.**

### ③ ExternalId — "혼란스러운 대리인(confused deputy)" 방지

우리 서비스는 여러 사용자를 대신해 AWS에 접근하는 **대리인**이다. 대리인 구조에는 고전적인
취약점이 있다:

> 공격자가 **남의 Role ARN**을 알아내 우리 서비스에 자기 계정인 척 등록한다.
> 우리는 그게 남의 것인지 모르고, 우리 신원으로 그 역할을 빌려 그 사람의 리소스를 보여준다.

ExternalId는 이걸 막는다. 역할의 신뢰 정책에 "ExternalId가 `abc-123`일 때만 허용"이라고 적혀
있으면, 그 값을 모르는 공격자는 Role ARN을 알아도 들어갈 수 없다. **사용자마다 다른 값**을
발급해야 의미가 있다.

### ④ 임시 자격증명은 값이 3개다

기존 Access Key는 2개(ID + Secret)인데, 역할을 빌려서 받는 임시 자격은 **3개**다:

```
AccessKeyId  +  SecretAccessKey  +  SessionToken  (+ 만료 시각)
                                    ^^^^^^^^^^^^ 이게 추가된다
```

`SessionToken`이 "이건 빌린 자격이고 언제까지 유효하다"는 증표다. AWS SDK와 Terraform 모두
`AWS_SESSION_TOKEN` 환경변수 또는 파라미터로 이 값을 받는다.

> **우리 코드에서 유리했던 점**: `app/providers/aws.py`의 SDK 세션 생성부와 AWS 프로비저닝
> 러너 4개(`ec2`/`rds`/`s3`/`cloudfront`)가 **이미 `session_token`을 받도록 짜여 있었다.**
> 그래서 "임시 자격을 발급하는 단계"만 앞에 붙이면 하류 코드는 그대로 동작한다.

## 4. 토큰 발급 과정 — 요청 하나가 처리되는 순서

사용자가 "EC2 생성"을 눌렀을 때 실제로 일어나는 일:

```
1. 사용자 요청
      │
2. 서버: DB에서 credential 조회 → 복호화
      │  얻는 값: { role_arn, external_id }   ← 비밀 아님
      │
3. 서버: 자기 신원(플랫폼 IAM 사용자)으로 STS에 요청
      │  sts:AssumeRole(
      │      RoleArn        = 사용자의 역할,
      │      ExternalId     = 확인용 값,
      │      RoleSessionName= 누가 왜 빌렸는지 기록용,
      │      DurationSeconds= 3600 )
      │
4. AWS STS: 신뢰 정책을 검사 → 통과하면 임시 자격 3종 발급
      │  { AccessKeyId, SecretAccessKey, SessionToken, Expiration }
      │
5. 서버: 이 값으로 boto3 세션 생성 / Terraform 환경변수 주입
      │  ※ 메모리에만 존재. DB에 저장하지 않고, 로그에도 남기지 않는다.
      │
6. 작업 완료 → 자격 폐기
      │
7. (설령 안 지워도) 1시간 뒤 AWS가 자동 무효화
```

4번의 **신뢰 정책 검사**가 보안의 실제 관문이다. 여기서 세 가지를 동시에 본다:

1. 요청자가 신뢰 정책에 적힌 그 계정인가
2. ExternalId가 일치하는가
3. 요청자 쪽에도 `sts:AssumeRole` 권한이 있는가

셋 중 하나만 틀려도 `AccessDenied`다.

## 5. 유출 시 피해 비교 (발표에서 가장 잘 먹히는 슬라이드)

| 유출된 것 | 기존 방식 | 변경 후 |
|---|---|---|
| DB 덤프 | 암호화돼 있어 즉시 피해는 없음 | 동일 + **애초에 비밀이 없음** |
| 서버 침해(복호화 키 포함) | **전 사용자의 영구 키 노출.** 사용자가 직접 폐기할 때까지 유효 | `role_arn`·`external_id`만 노출 → **그 자체로는 무권한** |
| 우리 플랫폼 키 | — | `sts:AssumeRole` 권한만 있음. 우리를 **이미 신뢰하도록 설정한** 역할만, **ExternalId까지 맞아야** 빌릴 수 있음 |
| 사용자의 대응 | 키를 직접 찾아 폐기해야 함 | 자기 계정에서 **역할만 지우면 즉시 차단** |

마지막 줄이 특히 중요하다 — **통제권이 사용자에게 돌아간다.** 우리 서비스에 로그인하지 않고도
자기 AWS 콘솔에서 언제든 접근을 끊을 수 있다.

## 6. 왜 AWS만 했나 (예상 질문 대비)

| | 표준 방식 | 상태 | 이유 |
|---|---|---|---|
| AWS | Cross-account Role + `sts:AssumeRole` | **전환 완료** | 업계 표준(다수 SaaS가 동일). 우리 코드가 이미 세션 토큰을 받고 있어 전환 비용이 가장 낮았다 |
| GCP | Service Account Impersonation | 현행 유지(후속) | 기술적으로는 AWS와 대등하게 가능하나, 어댑터 3곳(`verify`/`action`/`discover`)과 러너 4개를 모두 바꿔야 해 작업량이 3~4배다 |
| Azure | Lighthouse(위임된 리소스 관리) | 현행 유지 | 온보딩 모델 자체가 다르다(고객이 ARM 템플릿 배포). 검증하려면 테넌트가 2개 필요해 이번 범위에서 제외했다 |

**"3사를 동일한 방식으로 맞추는 것"은 애초에 올바른 목표가 아니다.** 세 CSP의 위임 모델이
서로 다른 물건이라, 실무 멀티클라우드 SaaS도 provider마다 연결 절차가 다르다. 우리 코드는
이미 provider별 어댑터 구조라 이 비대칭을 그대로 담을 수 있다.

## 7. 남아 있는 한계 — 먼저 말하는 편이 낫다

**우리 서비스 자신의 장기 키 1개는 아직 남는다.** 역할을 빌리려면 "우리가 누구인지"를 증명해야
하는데, 지금은 로컬 도커로 돌기 때문에 그 신원을 `.env`의 Access Key로 갖고 있다.

그래서 이 전환의 정확한 성과는 이렇게 말해야 한다:

> **"비밀키를 0개로 만들었다"가 아니라, "사용자 수만큼 늘어나던 영구 키(N개)를 우리 것 1개로
> 줄였다."** 그 1개도 서버를 AWS 위(EC2 인스턴스 역할 / ECS Task Role)에 올리면 AWS가 직접
> 임시 자격을 주입하므로 **0이 된다** — 배포 단계의 후속 과제다.

또 하나: **기존에 Access Key로 등록한 계정은 자동 전환이 불가능하다.** 우리가 원본 키를 따로
보관하지 않기 때문에(보관했다면 그것 자체가 문제다), 사용자가 역할을 새로 만들어 다시 등록해야
한다. 그래서 두 방식을 **병존**시키고 기존 등록분은 그대로 동작하게 뒀다.

## 8. 예상 질문 & 답변

**Q. 결국 우리 키가 유출되면 똑같은 거 아닌가?**
아니다. 그 키에는 `sts:AssumeRole` 권한 하나뿐이고, 빌릴 수 있는 대상도 **이미 우리를 신뢰하도록
설정해 둔 역할**로 한정된다. 게다가 사용자별 ExternalId까지 맞아야 한다. 기존 방식에서 유출됐을
때 "전 사용자의 계정에 무제한 접근"이 되던 것과는 피해 규모가 다르다.

**Q. IAM Identity Center(SSO)로 로그인하게 하는 게 아니고?**
그건 **사람이 우리 서비스에 로그인하는 방법**을 바꾸는 것이고, 지금 문제("남의 키를 보관한다")는
**우리 서버가 클라우드에 접근하는 방법**이라 층이 다르다. 게다가 우리 서비스는 리소스 동기화와
Terraform 실행이 **백그라운드에서** 도는데, 사용자 로그인 세션에 묶인 토큰은 브라우저를 닫으면
갱신할 수 없어 그 기능들이 동작하지 못한다.

**Q. 1시간 안에 안 끝나는 작업이 있으면?**
현재 Terraform 실행 타임아웃이 **15분**이라 토큰 수명(1시간)의 1/4이다. 더 긴 작업이 필요해지면
자동 갱신되는 자격증명(refreshable credentials)으로 바꾸면 된다.

**Q. 사용자가 역할에 관리자 권한을 주면 똑같지 않나?**
권한 범위를 **사용자가** 정한다는 게 핵심이다. 기존에는 사용자가 붙여넣은 키의 권한을 우리가
그대로 상속받았지만, 이제는 사용자가 역할 권한을 좁히면 우리가 할 수 있는 일도 그만큼 줄어든다.
통제권이 반대편으로 넘어간 것이다.

**Q. 역할 이름을 꼭 정해진 대로 만들어야 하나?**
우리 플랫폼 키의 권한을 `MultiCloudOps*` 접두사로 제한해 뒀다. 이건 **우리 키가 유출됐을 때의
피해 범위를 줄이기 위한 것**이지 보안의 관문은 아니다 — 실제 관문은 고객 쪽 신뢰 정책이다.
필요하면 이 패턴은 설정값으로 조정할 수 있다.

## 9. 용어 한 줄 정리

| 용어 | 뜻 |
|---|---|
| **IAM 역할(Role)** | 소유자 없이 조건을 만족하면 빌려 쓰는 권한 묶음 |
| **신뢰 정책(Trust Policy)** | 역할을 **누가 빌릴 수 있는지** 정하는 문서 |
| **권한 정책(Permission Policy)** | 역할로 **무엇을 할 수 있는지** 정하는 문서 |
| **STS** | AWS Security Token Service. 임시 자격증명을 발급하는 서비스 |
| **AssumeRole** | 역할을 빌려 임시 자격증명을 받는 STS API |
| **ExternalId** | 대리인 구조에서 "진짜 그 고객이 맞는지" 확인하는 공유 값 |
| **SessionToken** | 임시 자격증명임을 증명하는 세 번째 값 |
| **Cross-account** | 서로 다른 AWS 계정 사이의 접근 |
| **Confused deputy** | 대리인이 속아서 권한 없는 접근을 대신 수행하는 취약점 |
