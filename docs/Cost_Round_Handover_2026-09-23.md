## 1. 먼저 볼 것 세 가지

### 1-1. ⚠️ 전망(월말 예상 비용) 계약이 상충한다 — 숫자가 틀릴 수 있다

| | 1단계(#118, 승인된 결정) | 현재 구현(#128, 2026-09-22) |
|---|---|---|
| 수집이 빠진 날이 있을 때 | **전망을 내지 않는다**(`forecast_status.state = insufficient_coverage`) | **계산한다.** 빠진 계정·일수는 안내만 |
| 분모 | — | **달력 경과일수**(오늘이 이달 며칠째인가) |
| 분자 | — | 실제로 수집된 날의 합계 |

지금 방식은 빠진 날의 비용이 **분자에서만 빠지고 분모에는 남아서**, 수집 지연이 있으면 전망이
**실제보다 낮게** 나온다. 원래 계약("미수집일을 0으로 평균 내지 않는다")이 막으려던 것이 바로 이
상황이다. 어느 쪽을 최종 계약으로 할지 **정해야 한다**. 정해질 때까지 이 값은 참고치다.

- 관련 코드: `backend/app/cost/query.py::forecast_month_end`
- 문서: `docs/01_API_Specification_v1.2.md` §11-4(같은 내용을 계약 옆에 적어 뒀다)
- 화면: 프론트는 **어느 쪽도 따라가지 않고** 서버가 준 상태를 그대로 문구로 옮긴다. 모르는 상태가
  오면 "이 조건에서는 전망을 내지 않습니다"로 표시한다.

### 1-2. 카테고리 매핑표가 두 곳에 있다

`GET /costs/breakdown?dimension=category`가 쓰는 "AWS 서비스명 → 카테고리" 표가 두 벌이다.

| 위치 | 소유 | 상태 |
|---|---|---|
| `backend/app/cost/query.py::_AWS_SERVICE_TO_CATEGORY` | 비용(이승현) | **2026-09-23 수정** — 실제 Cost Explorer 정식 명칭 키 추가 |
| `backend/app/report_cost.py::_SERVICE_TO_CATEGORY` | 보고서(안권형) | 같은 버그를 피하려고 따로 둔 우회표(2026-09-21) |

두 표의 **값은 일치**하도록 맞췄다(대조 결과 불일치 0건). 다만 한쪽만 고치면 화면과 보고서가 갈라지는
구조라 **단일 소스로 합치는 것이 후속 과제**다(소유가 갈려 이번에 합치지 않았다).

**무엇이 고쳐졌나**: 매핑 키가 `AmazonEC2` 같은 짧은 코드뿐이었는데 실제 Cost Explorer는
`Amazon Elastic Compute Cloud - Compute`처럼 **정식 명칭**을 준다. 개발 DB의 실수집 서비스 15종 중
매칭이 0건이라 카테고리 집계가 **전액 "미분류"**였다. → **대시보드(`dashboard.js`)의 카테고리 카드가
실측 대신 조용히 "추정치"로 내려가 있었다.** 이제 실측 기준으로 보인다.

> 실데이터 기준 변화(읽기 전용 확인): 미분류 100% → `compute 58.5% · db_rdbms 22.4% ·
> storage_object 0.0% · 미분류 19.1%`. 카테고리 어휘는 `service_catalog`의 4종
> (`compute`·`db_rdbms`·`storage_object`·`cdn`)이 전부라, VPC·Secrets Manager·CloudWatch 같은
> 네트워크·보안 계열은 **여전히 미분류**다. 어휘를 늘리면 대시보드의 `CATEGORY_LABEL`(4종)이 모르는
> 키를 조용히 버리므로, **어휘 확장은 화면 담당자와 함께** 정해야 한다.

### 1-3. 비용 조회 API에 필드가 늘었다 (구현 완료)

`docs/01_API_Specification_v1.2.md` §11-4·§11-7·§11-8에 반영했다. 요지만:

| 필드 | 어디 | 뜻 |
|---|---|---|
| `accounts[].coverage` | `/costs/summary`, `/costs/collection-status` | 조회 기간에서 **수집이 확인된 날**. `null`이면 판정 대상 아님. 개수는 반드시 `missing_count`(목록 `missing_days`는 31개에서 잘리고 `truncated`가 뜬다) |
| `accounts[].filter_excluded` | `/costs/summary` | `"currency"`면 **통화 조건** 때문에 빠진 것(수집 문제 아님) |
| `kpis.forecast_status` | `/costs/summary` | 전망을 낸/못 낸 이유(응답 전체 단위) |
| `comparability` | `/costs/changes` | 비교 불가 **사유 코드**와 계정별 결측 |
| `warnings[].missing_count`·`accounts[]` | `/costs/summary` | 경고에 정확한 개수·대상 계정 |
| `currency` query | `/costs/changes` | 조회 6종 공통 필터와 같은 의미 |

**날짜 경계는 전부 UTC**다(`utc_today()`). 서버 로컬 시각을 쓰지 않는다 — KST 새벽 0~9시에 화면과
서버가 하루 어긋나던 문제가 여기서 왔다.

`"수집 확인"의 정의`는 한 곳(`backend/app/cost/coverage.py`)에만 있다: **그 날 행이 있거나, 성공한
수집 run의 범위에 든 날**. $0인 날은 행이 생기지 않으므로 행 유무만 보면 정상 0원 계정이 영원히
결측으로 보이기 때문이다. 예산 결측 판정·급증 판정도 같은 함수를 쓴다.

## 3. 이번 라운드에서 고친 문제 (요약)

| # | 문제 | 수정 | 사용자에게 좋아지는 점 |
|---|---|---|---|
| 1 | 수집이 안 된 날을 0원처럼 합산·표시 | `coverage` 도입, "확인된 0원"과 "모름"을 구분 | 화면의 0원을 믿을 수 있다 |
| 2 | 전망·비교가 "왜 안 나오는지" 말하지 않음 | `forecast_status`·`comparability` 사유 코드 | 빈 카드 앞에서 원인을 추측하지 않아도 된다 |
| 3 | KST 새벽 0~9시에 화면·서버 날짜가 어긋남 | 전 구간 UTC 기준 통일(예산 포함) | 새벽에 조회해도 같은 기간을 본다 |
| 4 | 통화가 섞이면 상위 5개에서 한 통화가 통째로 사라짐 | 통화별 섹션으로 분리(각 통화 상위 N) | KRW·USD를 함께 쓰는 계정에서 값이 사라지지 않는다 |
| 5 | 버튼이 말과 다른 일을 함(재수집 대상 불명확, 상세가 요약값 재사용) | 대상 계정 id를 명시해 전송, 상세는 `top_n=20` 재조회 | 누르기 전에 무엇이 일어날지 알 수 있다(과금 호출 포함) |
| 6 | 카테고리 집계가 전액 미분류 | 실제 서비스명 매핑(1-2) | 대시보드 카테고리 카드가 실측을 보여준다 |
| 7 | 종결한 검토 항목을 다시 볼 수 없음 | 미처리/종결/전체 전환(기존 API 재사용) | 처리 이력과 종결 사유를 확인할 수 있다 |
| 8 | 같은 분석을 다시 열 수 없음 | 탭까지 URL에 담고 "조건 링크 복사" | 본 화면을 그대로 공유·복원할 수 있다 |
| 9 | 도커 이미지에 `.venv`가 들어가 2.11GB | `backend/.dockerignore` | 빌드·배포가 빨라진다(918MB) |

## 4. 검증 상태 — **끝난 것과 안 끝난 것**

- 백엔드 테스트 **865개 통과**(`cd backend && TZ=UTC DATABASE_URL=... pytest -q`).
- 프론트는 jsdom 상태 주입 픽스처 **70개 통과**(①② 27 · ③ 21 · 동작 12 · 5단계 10)와 Chrome 자동화
  실 GET 확인 **32항목**. 이 픽스처·스크립트는 `docs/비용_개발문서/verify/`에 있고 **저장소에 올라가지
  않는다** — 재현이 필요하면 요청하면 tracked 경로로 옮긴다.
- ⚠️ **jsdom 통과는 브라우저 확인이 아니다.** 사람이 눈으로 봐야 하는 항목 **10건**이 남아 있다
  (모달 스크롤·다크 테마·A4 인쇄 실물·뒤로 가기·클립보드 권한 등). 발표 리허설에서 확인 예정.
- ⚠️ **실제 CSP 재수집(과금 호출) 경로는 한 번도 실행하지 않았다.** 화면·요청 본문까지만 확인했다.
